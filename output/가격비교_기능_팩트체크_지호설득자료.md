# 가격 비교 기능, 메인으로 둘 것인가 — 리소스 팩트체크


지호에게.

먼저 분명히 해둘게. 이 글은 "가격 비교 빼자"는 글이 **아니야.** 네가 가격 비교에 끌리는 이유에는 분명히 맞는 부분이 있고, 그건 아래에서 먼저 인정하고 시작할게. 다만 한 가지 질문을 정확한 사실로 같이 따져보자는 거야:

> **가격 비교를 사이트의 "메인"으로 둘 만큼, 이 기능이 정말 가벼운가?**

결론부터 말하면 — 가볍지 않아. 오히려 우리가 계획한 기능들 중 **만들고 유지하는 비용이 가장 비싼 기능**이야. 왜 그런지 근거를 하나씩 보자.


## 1. 네가 맞은 부분 (먼저 인정)

- 가격 비교는 **직관적으로 유용**해. "이 작품 어디서 제일 싸게 보지?"는 누구나 한 번쯤 하는 생각이야.
- **차별화 포인트**가 될 수 있다는 감각도 맞아 — 실제로 이걸 제대로 하는 경쟁 서비스가 거의 없거든(뒤에서 설명).
- "있어서 나쁠 거 없다"도 **조건부로 맞아.** 진짜 가벼운 형태라면 두는 게 좋아. 핵심은 *어떤 형태로* 두느냐야.

그러니 이 글의 목표는 "빼라"가 아니라, **"무거운 버전(가격 비교 엔진)을 메인에 두면 프로젝트가 가라앉는다. 가벼운 버전으로 살리자"**를 데이터로 보여주는 거야.


## 2. 가장 중요한 사실: 가격 데이터는 가져올 API가 없다


### 먼저 — "API 있잖아"에 대하여 (네 말도 맞아)

네가 말한 API, 기획서에 분명히 적혀 있어. `New Fairtoon Website Plan`의 "How Data will be Collected and Maintained"에 이렇게 돼 있지:

> "...a **hybrid approach** of pulling **generic metadata from an existing API** and **manually collecting and storing data on a spreadsheet**. For constantly changing data, like **user ratings or popularity ranking**, an API should be used."
> Places to Gather Data: **AniList API · MangaUpdates API · Kitsu API · Official Platforms**

그러니까 "API가 있다"는 말은 **절반은 맞아.** AniList·MangaUpdates·Kitsu API는 실제로 존재하고, 우리 사이트에 **꼭 필요해.** 단 — 이게 핵심인데 — 이 API들이 주는 건 **평점·인기순위·장르·작가·줄거리 같은 '메타데이터'**야. 작품 상세페이지의 "평점·반응", "장르 정보" 블록을 채우는 데 쓰는 거지.

**문제는, 이 API들 중 어느 것도 '가격'을 주지 않는다는 거야.** AniList·Kitsu·MangaUpdates는 애니/만화 메타데이터 DB라서, **회차당 가격·쿠키·캐시 같은 데이터 필드가 아예 없어.** (라이선스 정보조차 "있다/없다" 수준이고 지역·가격은 안 줘.) ([API 비교 자료](https://www.achriom.com/blog/myanimelist-vs-anilist-vs-kitsu/))

그리고 결정적으로 — **기획서 너 자신이 이미 그렇게 나눠놨어.** 위 문장을 다시 봐: API는 "generic metadata / ratings / popularity"에, **가격 같은 나머지는 "manually collecting and storing data on a spreadsheet(수동 수집·저장)"**에. 즉 *가격 데이터는 처음부터 "수동"으로 분류돼 있었어.* API로 해결되는 부분이 아니야.

> ✅ 한 줄 정리: **메타데이터 API는 있다(맞음). 가격 비교 데이터를 주는 API는 없다(이게 문제의 핵심).** "Official Platforms"가 목록에 있지만, 아래에서 보듯 거기엔 가져올 공식 API가 없어서 결국 사람 손이 들어가.


### 그래서, 가격 데이터는 어떻게 가져오나

가격 비교를 하려면 네이버 웹툰·카카오페이지·리디·네이버 시리즈의 **가격 데이터를 어디선가 계속 가져와야** 해. 그런데:

- **공식 가격 API가 없어.** 네이버 웹툰은 서버사이드 렌더링이라 HTML을 직접 긁어야(scraping) 하고, 카카오페이지는 비공개 GraphQL이라 **공식 문서도 없이** 클라이언트 요청을 역분석해야 해. ([참고](https://github.com/HyeokjaeLee/korea-webtoon-api))
- 개발자들이 만든 **제3자 웹툰 API**(korea-webtoon-api 등)가 있긴 한데, 이건 제목·작가·썸네일·장르 같은 **목록 정보만** 줘. **가격 정보는 아예 없어.** 그리고 비공식 스크레이핑 기반이라 플랫폼이 화면을 바꾸면 깨져.
- 우리가 기획서에서 쓰려던 **AniList·MangaUpdates·Kitsu API**는 애니/만화 메타데이터(평점·장르·줄거리)용이야. **한국 플랫폼 가격이나 이용가능성은 안 담겨 있어.** ([AniList API 문서](https://docs.anilist.co/))

➡️ 정리하면: 가격 데이터는 **API로 못 가져와.** 방법은 둘뿐이야 —
(a) 플랫폼마다 스크레이퍼를 직접 만들고 깨질 때마다 고치거나,
(b) 사람이 손으로 입력하거나.
둘 다 **"한 번 만들면 끝"이 아니라 영원히 반복되는 노동**이야.


### '최신 회차' 정보는 API로 되지 않나? — 같은 한계야

"가격은 그렇다 쳐도, 최신 회차 정보는 API로 가져오면 되잖아?" 싶을 수 있어. 정확히 나눠서 보자.

**API가 주는 것 (느리게 변하는 데이터 ✅)**
- 연재 상태(연재중/완결), 총 회차 수, 권 수, 연재 시작·종료일 → AniList·Kitsu가 줘.
- ⚠️ 단, 총 회차 수는 **완결작에서만** 신뢰도가 높아. 연재중 작품은 비어있거나(null) 부정확한 경우가 많아.
- '새 회차가 올라왔다'는 알림 → MangaUpdates가 RSS로 추적해(이게 이 서비스의 본업).

**API가 못 주는 것 (우리가 진짜 필요한 것 ❌)**
- "네이버에서 무료공개 N화까지 / 최신 유료화차는 언제 업데이트" 같은 **플랫폼별 최신화 + 무료 범위 + 업데이트 날짜.**
- MangaUpdates의 회차 추적은 **글로벌·영어권 스캔레이션/영문 릴리스 중심**이라, 한국 공식 플랫폼(네이버·카카오)의 회차별 무료/유료 상태는 추적하지 않아.

➡️ 즉 네가 상세페이지에 넣고 싶어한 "플랫폼별 최신 회차 + 무료 범위"도 **가격과 똑같이 수동·스크레이퍼 영역**이야. 구조를 한 줄로 보면:

> **느리게 변하는 데이터**(상태·총회차·평점·장르) = API 자동화 가능 ✅
> **플랫폼별로 빠르게 변하는 데이터**(가격 · 최신 무료화차 · 업데이트일) = API 없음 → 수동·스크레이퍼 ❌

그러니까 비싼 건 "가격" 하나가 아니라 **'플랫폼별 실시간 데이터' 층 전체**야. 가격을 빼도 최신화·무료범위를 실시간으로 정확히 유지하려 하면 똑같은 함정에 빠져. (그나마 '새 회차 떴다'는 거친 신호만 MangaUpdates로 일부 자동화될 뿐이야.)


## 3. '가격'은 숫자 하나가 아니라 조건 덩어리다

가격 비교가 가벼울 거라는 착각은 "작품마다 가격 숫자 하나만 적으면 되지"라는 생각에서 와. 실제는 이래:

- 네이버는 **쿠키**, 카카오는 **캐시**, 리디는 또 다른 단위 — 통화부터 다름.
- 같은 작품도 **대여 vs 소장** 가격이 다르고, **기다리면 무료**(타이머), **광고 보고 무료**, **타임딜**, **세트 할인**, **무료 선공개 회차 수**가 다 따로 놀아.
- 즉 한 작품의 "가격"은 **숫자가 아니라 조건표(rule set)**야. 이걸 4개 플랫폼에서 정규화해서 "비교"하려면 데이터 모델도 UI도 복잡해져.

이건 빌드 비용을 키우는 동시에, 아래 4번 때문에 **유지 비용을 폭발**시켜.


## 4. 정책이 예고 없이 바뀐다 (실제 사례)

가격/정책은 가만히 있지 않아. 최근 실제 사례:

- **WEBTOON이 2025년 5월 29일 Daily Pass를 폐지**했어. 그동안 Daily Pass로 무료로 보던 작품들이 **회당 3코인 유료로 전환**됐지. 공식 공지(Product Change)는 폐지 **다음 날인 5월 30일**에 나왔어. ([Comics Beat](https://www.comicsbeat.com/no-youre-not-losing-it-webtoon-got-rid-of-daily-pass-2/), [Anime News Network](https://www.animenewsnetwork.com/news/2025-06-05/webtoon-service-ends-daily-pass-feature/.225053))

이게 무슨 뜻이냐면 — 우리가 어제 정확히 적어둔 가격이, 오늘 **공지보다 먼저 틀려버린다**는 거야. 그리고 가격 비교 사이트의 **유일한 가치는 정확성**이야. 추천 글은 틀려도 "의견"으로 넘어가지만, "여기가 더 싸다"가 한 번 틀리면 사람들은 **"이 사이트 못 믿겠다"**가 돼. 신뢰는 100개 맞아도 1개 틀리면 깨지는 비대칭 자산이야.

(참고로 이건 우리만의 문제가 아니야. 영상 쪽 JustWatch도 "표시가 자주 틀린다"는 불만을 받고, Skyscanner는 표시가-결제가 불일치로 규제까지 갔어. 가격 데이터는 원래 이렇게 위험해.)


## 5. 결정타: 비교할 대상이 거의 없다

여기가 제일 중요해. 한국 웹툰은 **독점 연재가 지배적**이야. 오리지널 독점 비중이 약 66%이고, 네이버 시리즈는 1년 이상 독점, 웹툰화 계약은 3~4년간 타 플랫폼 버전을 막아. ([나무위키 웹툰/시장](https://namu.wiki/w/%EC%9B%B9%ED%88%B0/%EC%8B%9C%EC%9E%A5))

즉 **대부분의 작품은 합법 플랫폼이 딱 하나**야. 그러면 "가격 비교" 화면에 **줄이 하나만** 떠. 비교가 안 돼.

그래서 경쟁 서비스(Kenmei, Anime-Planet, MangaUpdates, MyAnimeList 등) **누구도 가격 비교를 안 해.** 이건 "아무도 발견 못 한 빈틈"이 아니라 **"해봤자 비교할 게 없어서 안 하는" 구조적 이유**가 있는 거야.


## 6. 비용 합산 — 솔직한 추정

(아래 시간은 추정치야. 정확한 숫자가 아니라 "규모(order of magnitude)"를 보여주려는 거야.)

**만드는 비용 (1회성)**
- 플랫폼 4개 스크레이퍼 각각 제작(통화·조건 다름) **또는** 수동 입력 체계 구축
- 4개 서로 다른 가격모델을 비교 가능한 형태로 정규화하는 데이터·UI 설계

**유지 비용 (영원히 반복 — 진짜 문제)**
- 수동 재확인: 작품당 플랫폼 교차확인 2~3분 × 150~300편 = **회당 5~15시간**. 신뢰 유지하려면 최소 월 1회 → 사실상 **매달 반복되는 파트타임 노동**.
- 스크레이퍼 방식으로 바꾸면 그 노동이 **"깨진 스크레이퍼 수리"**로 바뀔 뿐, 사라지지 않아.
- 너는 고등학생이고, 학업과 병행해서 이 사이트의 *다른* 기능(가용성 탐색, 기사, 작가 인터뷰)도 만들어야 해. **새 기능 만들 시간과 가격 데이터 갱신할 시간을 동시에 가질 수 없어.** 결국 둘 다 부실해지는 악순환에 빠져.

**핵심 모순**: 가격 비교는 **유지 비용은 제일 비싼데, (5번 때문에) 대부분 작품에서 보여줄 게 없는** 기능이야. 가장 비싼 기능을 사이트의 중심에 두는 건 위험해.


## 7. 그래서 제안 — 네 아이디어를 살리는 가벼운 버전

가격 비교를 **버리지 말고, 무거운 부분만 덜어내자.** 두 가지로 나눠서 생각하면 돼:

| | 무거운 버전 (메인 ❌) | 가벼운 버전 (보조 ✅) |
|---|---|---|
| 형태 | 플랫폼별 실시간 정확한 가격을 긁어와 숫자로 비교하는 엔진 | 작품 상세 안에, 플랫폼별 **이용 방식 태그** 한 줄 |
| 데이터 | 쿠키/캐시 환산, 대여/소장, 이벤트까지 정확히 | **무료 / 기다리면 무료 / 유료** 정도의 분류 |
| 갱신 | 예고 없이 바뀜 → 상시 추적 필요 | 이용 *방식*은 정확한 *가격*보다 훨씬 덜 바뀜 |
| 신뢰장치 | 틀리면 즉시 불신 | **"최종 확인: YYYY-MM-DD"** 표시로 방어 |
| 비용 | 매우 높음 (6번) | 낮음 — 이게 "있어서 나쁠 거 없는" 버전 |

**구체적으로:** 작품마다 "어디서 합법으로 볼 수 있나"를 보여줄 때, 각 플랫폼 옆에 `무료` / `기다무` / `유료` 같은 **이용 방식 라벨**과 **최종 확인일**만 붙이는 거야. 정확한 원화 가격을 실시간으로 비교하는 엔진은 만들지 않아.

- 이러면 네가 원하던 "가격 정보"는 **살아있어.**
- 스크레이퍼도, 통화 환산도, 실시간 추적도 필요 없어서 **1인이 유지 가능해.**
- 한 줄짜리 분류라 틀릴 일도 적고, "최종 확인일"이 있으면 신뢰도 지켜져.

그리고 사이트의 **메인 자리는** 더 가치 있고 덜 바뀌는 일 — **"이 작품을 내 언어/지역에서 합법으로 볼 수 있는 곳 찾기(가용성)"** 에 주자. 가격은 그 안에 들어가는 작은 부품이 되는 거야.


## 8. 한 문장 요약

> 가격 비교는 **좋은 본능**이지만, **무거운 엔진 형태로 메인에 두면** API도 없고 정책도 수시로 바뀌고 비교할 작품도 적어서 **프로젝트를 가라앉혀.** 대신 **이용 방식 태그 + 최종 확인일**이라는 **가벼운 형태로 살리면**, 네 아이디어도 지키고 사이트도 산다.

같이 더 얘기하자. 이 가벼운 버전이면 받아들일 만한지 듣고 싶어.
